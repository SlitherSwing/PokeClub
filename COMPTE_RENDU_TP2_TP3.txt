1. TP2 : ORGANISER LE CODE ET GÉRER LES POKÉMON

Le but est de donner un rôle précis à chaque partie du projet.

- Le modèle Pokemon représente un Pokémon : nom, types, attaques, objet,
  nature, image et points. Il garde les règles métier, par exemple les types
  différents, les attaques non répétées, 0 à 32 points par statistique et
  66 points au maximum au total.
- Les enums PokemonType et PokemonNature définissent les valeurs autorisées.
- PokemonMapper transforme une ligne SQL en objet Pokemon et prépare les
  données de l’objet pour l’enregistrement.
- PokemonRepository utilise PDO pour lire et enregistrer les Pokémon.
  Les requêtes restent dans ce fichier, pas dans les vues.
- PokemonController prépare le formulaire, vérifie les demandes et appelle
  le repository. public/index.php choisit l’action demandée par l’URL.
- Les vues affichent le HTML. Les pages de création et de modification
  partagent leurs champs dans src/View/pokemon/form.php.

Les dossiers et noms de classes ont été harmonisés : Model, Mapper,
Repository, Controller et View. Dans cette adaptation du sujet, le joueur
Player correspond à Pokemon ; ProPlayer reste une classe distincte.

Concrètement, lors d’une création :
  1) Le navigateur ouvre /?page=pokemon-create.
  2) Le contrôleur prépare un formulaire vide et la vue l’affiche.
  3) À l’envoi, le serveur vérifie le jeton CSRF et les valeurs reçues.
  4) Si elles sont valides, il construit un Pokemon et demande sa sauvegarde.
  5) Le navigateur revient au formulaire avec un message de confirmation.
     Un rafraîchissement de cette page ne répète pas l’ajout.

Lors d’une modification, l’URL est /?page=pokemon-edit&id=1, avec un ID existant.
Le formulaire est rempli depuis l’objet lu en base. Le nouvel objet reçoit
l’ID d’origine avant save() : le repository fait un UPDATE, sans créer de doublon.
Un lien « Modifier ce Pokémon » est disponible sur les cartes de l’équipe.

En cas de saisie invalide, un message est affiché et la saisie est conservée.
La validation est commune aux deux actions. Le HTML reste échappé avec e(),
et les envois gardent leur protection CSRF. Les identifiants invalides ou
absents de la base sont refusés. L’ancien formulaire public de création a été
retiré après vérification ; l’ancienne URL d’édition redirige vers la route.

2. TP3, FICHE 03 : COMPOSER ET DEUX BIBLIOTHÈQUES

Composer est maintenant installé et gère les bibliothèques PHP du projet.
Il ne remplace ni MySQL ni PDO.

- composer.json décrit les dépendances, PHP et les extensions nécessaires.
  Son mapping PSR-4 associe le préfixe PokeClub\ au dossier src/.
- composer.lock conserve les versions exactes installées. Ces deux fichiers
  sont suivis dans Git pour pouvoir reproduire l’installation.
- vendor/ contient les bibliothèques et le chargeur généré. Il est ignoré
  par Git et se reconstruit avec composer install.
- Le bootstrap et les fixtures utilisent maintenant vendor/autoload.php.
  Le chargeur manuel a été supprimé après vérification de ses références.
  La session, les helpers et la connexion PDO ont été conservés.

Deux bibliothèques ont été installées, essayées séparément puis intégrées :

Symfony Validator 7.4.22
  Le contrôleur utilise Validation::createValidator(), NotBlank et Length
  pour vérifier que le nom est renseigné et ne dépasse pas 255 caractères.
  Les violations deviennent des messages français dans le formulaire.
  L’ancienne vérification du nom a été retirée pour éviter les doublons.
  Les autres contrôles et les règles métier du modèle sont conservés.

Monolog 3.12.1
  src/require/logger.php configure un journal dans var/log/pokeclub.log,
  hors du dossier public et ignoré par Git. Le logger est donné au contrôleur.
  Une erreur de création, modification ou lecture produit un message générique
  pour le visiteur. Le journal garde l’opération et les codes SQLSTATE/pilote,
  sans mot de passe, formulaire, nom saisi ni trace d’exception.

Le verrouillage contient huit paquets : ces deux bibliothèques et leurs
six dépendances. Les contrôles de compatibilité n’ont pas été contournés.

3. ENVIRONNEMENT ET COMMANDES POUR REPRENDRE

Vérifié avec PHP 8.5.10 et Composer 2.11.1.
Le projet demande PHP 8.3 minimum dans la branche 8.x. Le PHP 8.2.4 fourni
par XAMPP sur cette machine est trop ancien pour le code déjà présent.
MySQL peut rester démarré dans XAMPP ; servir PokeClub avec le PHP compatible :

  /opt/homebrew/bin/php -S localhost:8000 -t public

Ouvrir ensuite http://localhost:8000.

Depuis la racine du projet, pour installer les bibliothèques :

  composer install

Cette commande reproduit composer.lock. Ne pas utiliser composer update
simplement pour retrouver l’installation. La base et ses tables doivent déjà
exister ; Composer ne les crée pas. Les identifiants restent dans le fichier
local ignoré src/require/config.local.php. Le README détaille l’installation,
la génération du CSS et les vérifications.
